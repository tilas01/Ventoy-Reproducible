# The signing key

Every release carries a detached OpenPGP signature over `manifest.json` and over
`SHA256SUMS`. This page is the key's identity, how to check it, and how it is
looked after.

## The fingerprint

```
4E5F DAEA DF0E 4EB5 749F  7AB1 4FFA 1EB9 69BE 7BBD
```

Signing subkey: `44B1 0470 0010 51D7 73AB  7F31 A62B CE85 A4FD 3DC1`

The public key is at
[`docs/keys/ventoy-reproducible-signing-key.asc`](keys/ventoy-reproducible-signing-key.asc),
and is attached to every release as `signing-key.asc`.

### Checking the fingerprint against a second source

A key published beside the thing it signs proves nothing on its own: whoever
could replace the release could replace the key next to it. The fingerprint
above appears in three places that would have to be compromised together:

1. This file, in git, with the commit history that added it.
2. The website at
   [tilas01.github.io/Ventoy-Reproducible](https://tilas01.github.io/Ventoy-Reproducible/),
   written into the HTML rather than fetched, so a local copy of the site shows
   what the source says.
3. Every release page, in the notes.

Compare at least two before trusting a release. If they disagree, stop and open
an issue.

## Why the key is shaped this way

**A certify-only primary key, with a separate signing subkey.** The primary
key's only job is to certify the subkey. It stays offline. Day to day, and in
CI, only the subkey is used, and the subkey cannot certify: a compromised runner
therefore cannot mint a new identity under this key. If the subkey is ever
exposed it is revoked and replaced, and the fingerprint everybody has recorded
does not change.

**RSA 4096, and that is the real ceiling.** GnuPG will not generate larger
without being rebuilt, and larger RSA is not meaningfully stronger. The distance
between 3072-bit RSA and anything an adversary could actually attack is already
enormous, and beyond 4096 the extra cost falls on the people verifying rather
than on an attacker. There is no 8192-bit tier that buys security instead of
latency.

**The key at rest is protected with AES-256, SHA-512, and an S2K count of
65011712,** which is the largest value the OpenPGP format can encode. AES-GCM
does not appear here because OpenPGP does not use it for this: private keys are
protected with a cipher in CFB mode driven by a string-to-key function, and the
controls that exist are which cipher, which digest, and how expensive the S2K
is. All three are at their maximum.

**The passphrase is 256 bits from the system CSPRNG**, not chosen by a person. A
4096-bit key behind a guessable passphrase is a guessable key, and this is the
setting that actually decides how hard the private key is to open. It is not a
wordlist, because a passphrase that lives in a password manager is never typed
and memorability would only cost entropy.

**It expires in three years.** An expiry is a dead man's switch: if the project
is abandoned, the key stops asserting things rather than remaining valid for
ever. It can be extended at any time with the primary key.

Generated by [`tools/signing/generate-signing-key.sh`](../tools/signing/generate-signing-key.sh),
which is in the repository so the process is auditable rather than described.

## Where the private key lives

Three places, and no others:

| Where | What |
|---|---|
| The maintainer's password manager | The full private key, the passphrase, the revocation certificate |
| An offline backup | The same |
| GitHub Actions encrypted secrets | The **signing subkey only**, and the passphrase |

It is not in this repository and never will be. `.gitignore` excludes
`gpg_secrets/` and ignores `*.asc` by default, allowing back only the two paths
where a *public* key legitimately lives. Getting that rule the wrong way round
is unrecoverable in a way an accidentally committed build artefact is not:
untracking a file stops it being published from now on, and every version
already committed stays in the history for anyone who clones it.

## Putting the key into GitHub

Two repository secrets are needed. Both are set at
**Settings → Secrets and variables → Actions → New repository secret** in
`tilas01/Ventoy-Reproducible`, or:

```bash
gh secret set GPG_PRIVATE_KEY --repo tilas01/Ventoy-Reproducible \
  < gpg_secrets/private-subkey-FOR-CI.asc

gh secret set GPG_PASSPHRASE --repo tilas01/Ventoy-Reproducible \
  < gpg_secrets/passphrase.txt
```

| Secret | Contents |
|---|---|
| `GPG_PRIVATE_KEY` | `gpg_secrets/private-subkey-FOR-CI.asc`, the whole armoured block including the `BEGIN`/`END` lines |
| `GPG_PASSPHRASE` | The single line in `gpg_secrets/passphrase.txt`, with no trailing spaces |

**Use the subkey export, not the full key.** `private-key-FULL.asc` contains the
certifying primary key. Putting that on a build runner would mean a compromise
of GitHub Actions could issue new identities under this key, and the offline
primary would have been offline for nothing.

Once both secrets are set, delete `passphrase.txt` and `private-key-FULL.asc`
from the working machine. A secret in two places is twice as likely to leak and
no more available.

## When a build is unsigned

The secrets are absent on forks. A fork's build produces every artefact, no
signature, and an `UNSIGNED.md` in the release saying so:

> The signing key is a repository secret and is absent here, which is the
> expected state on a fork. Every artefact is present and the manifest is
> complete; what is missing is the maintainer's attestation that this is the
> build they made.

That is deliberate. A fork failing mysteriously at the signing step would look
like a broken build rather than an absent key.

## How signing happens

In `.github/workflows/release.yml`, after the manifest is written:

1. A throwaway `GNUPGHOME` is created on the runner.
2. The subkey is imported and marked ultimately trusted, because otherwise gpg
   waits for an interactive prompt that has nowhere to appear.
3. `manifest.json` and `SHA256SUMS` are signed with `--digest-algo SHA512`.
4. **The signature is checked with this project's own `ventoy-verify` before the
   release is published.** A release whose signature does not verify must never
   reach the release page, and the cheapest place to catch that is before it is
   created.
5. The `GNUPGHOME` is destroyed.

## Rotation and revocation

To rotate the subkey, which is the ordinary case:

```bash
gpg --edit-key 4E5FDAEADF0E4EB5749F7AB14FFA1EB969BE7BBD
# addkey, choose RSA sign-only, 4096, then save
gpg --armor --export-secret-subkeys <fpr> > new-subkey.asc
gh secret set GPG_PRIVATE_KEY --repo tilas01/Ventoy-Reproducible < new-subkey.asc
```

The published fingerprint does not change, so nobody has to do anything.

To revoke the whole key, which is the bad case, publish
`revocation-certificate.asc`, announce it in the repository and on the website,
and generate a new key. Anybody who has the old public key will see it as
revoked once they import the certificate.

The revocation certificate was generated at the same moment as the key, not
later. It cannot be produced after the key is lost, which is exactly the
situation it exists for.

## Verifying without `ventoy-verify`

```bash
gpg --import signing-key.asc
gpg --verify manifest.json.asc manifest.json
```

Read the fingerprint gpg prints and compare it with the one at the top of this
page. Do not skip that step: `gpg --verify` exits zero for a signature made by
**any** key in your keyring, and prints its warning about trust on a line that
is easy to miss.

`ventoy-verify` exists partly to remove that trap. It has no keyring, takes one
key file, and treats a signature from anything else as a failure rather than a
warning.
