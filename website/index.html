Ventoy-Reproducible

Trust is not verification, and Ventoy asks for trust 1079 times.

Ventoy is genuinely good software, and this is a fork of it rather than a criticism of it. Nothing here suggests its authors have done anything wrong.

The problem

Ventoy's repository contains 1079 executable binaries: 754 committed as loose ELF and PE files, and a further 325 committed compressed, which a running system unpacks and executes. Bootloaders, EFI drivers, 59 kernel modules, Windows executables. When you install Ventoy, those exact files are written to your USB stick, and your computer runs them before your operating system starts.

Not one of them was compiled by anybody outside the project.

There is no build you can watch and no way to check that ventoy_x64.efi is what its source compiles to. You can read every line of the C, and it tells you nothing about the binary next to it. The source being open does not make the binary open.

That is an absence, not an allegation. Those binaries are probably clean. But probably is not a security property, and today no reader can do better than probably however careful they are.

What this fork does

Every binary is compiled by GitHub Actions, from source you can read, in a container pinned by digest, with every compiler pinned by SHA-256. Each is built twice, in two differently named directories, and a one-byte disagreement is reported as a failure.

The result is a signed manifest naming every file with its size, SHA-256 and BLAKE3. And the part most projects leave out: the manifest and its report name every file that did not reproduce and every file this project could not build at all.

Use it

Check a release

# Download a release, then one command:
ventoy-verify release --key signing-key.asc

It checks the signature over the manifest first, and reads nothing from the manifest until that passes. Then it hashes every file and prints failures first. 

OK signature over manifest.json is good
   made by a signing subkey of 4E5F DAEA DF0E 4EB5 749F 7AB1 4FFA 1EB9 69BE 7BBD

1079 files checked
  1079 matched the manifest
    1059 compiled by this project's CI
    20 third-party binaries, pinned by hash and not built here

PASSED. every file matches the manifest.

Exit 0 passed, 1 a verification failure, 2 the check could not run. In a script, “the release is bad” and “you typed the wrong path” deserve different reactions.

Build the verifier

git clone https://github.com/tilas01/Ventoy-Reproducible
cd Ventoy-Reproducible/tools/ventoy-verify
cargo build --release --locked

# a window instead, if you would rather not use a terminal
cargo build --release -p ventoy-verify-gui

Count the binaries yourself

python3 tools/inventory/inventory.py --print-counts
1079executable binaries in the tree 754…committed loose, as ELF or PE 325…committed compressed, unpacked at runtime 182paths named in upstream's BLOB_List.md 903present but not named anywhere 859…of those, GRUB2 modules 59…Linux kernel modules, named by nothing

The 859 GRUB2 modules are covered collectively by one build instruction rather than named, which is reasonable. The 59 Linux kernel modules are covered by nothing. This is the ordinary drift of a hand-maintained list beside a generated set, which is why this project derives its inventory by machine on every run, from magic bytes rather than from file names.

Rebuild it all yourself

export SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct)
bash tools/build/fetch-toolchains.sh toolchains/cache
# then the container command in docs/REPRODUCIBLE_BUILDS.md

It never falls behind Ventoy

A fork that goes stale is worse than no fork: it offers the reassurance of a verified build while shipping a version with bugs upstream fixed months ago, and the reassurance is the part people remember.

A scheduled workflow checks ventoy/Ventoy every three hours. New commits are merged and rebuilt. A new upstream release is built and published here as <upstream tag>+repro.N, so you can always tell which Ventoy you are holding. If a merge conflicts it stops and opens an issue rather than guessing, because this is a repository full of bootloaders.

main is the only branch published. Development happens elsewhere and reaches it as a merge, so the public history is the history of what was released.

The signing key

4E5F DAEA DF0E 4EB5 749F 7AB1 4FFA 1EB9 69BE 7BBD

RSA 4096, certify-only primary with a separate signing subkey. This fingerprint is written into this page's HTML rather than fetched, so a local copy of the site shows what the source says. Compare it against docs/SIGNING.md and the release notes before trusting a release: a key published beside the thing it signs proves nothing on its own.

ventoy-verify has no keyring, and that is the point. gpg --verify exits zero for a signature made by any key you have ever imported, so somebody who once imported a key from a forum post gets a green tick. This tool takes one key file and treats a signature from anything else as a failure, naming both fingerprints.

What this does not prove

This is the part that makes the rest credible, so it is on the page rather than in an appendix.

  • A reproducible build proves a binary follows from its source. It does not prove the source is safe. Nobody here has audited Ventoy's C.
  • It does not prove the compiler is honest. Four of the seven pinned toolchains are prebuilt binaries with no canonical source. A backdoored compiler produces a perfectly reproducible backdoor.
  • Pinning a compiler by hash fixes which unverified compiler you get. That is a smaller claim than it sounds.
  • Reproducibility is per-target. An x86-64 build reproducing says nothing about aarch64.
  • Twenty files are third-party binaries that can only be pinned, never built here. They are counted separately, everywhere.
  • Most of the 1079 are not yet built by this project. Every unbuilt path is named with a reason in every manifest.
  • The builds run on GitHub's infrastructure. The detached signature narrows what a compromise there could achieve; it does not eliminate it.
